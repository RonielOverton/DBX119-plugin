## Manual steps for the owner

Build with `cmake --build build --config Release`, then load `build/RTO119_artefacts/Release/VST3/RTO 119 Compander.vst3` in a DAW with plugin delay compensation (PDC). Standalone does not apply PDC, so use a DAW for steps 1 to 4. Unless a step says otherwise: Amount 0, Output 0 dB, Stereo Link on, Mode Linear, Iron off at first load.

Required by the operator (run these first):

1. **Iron toggle, no sweep (row 28).** Loop a stereo drum break. Toggle Iron on and off several times. Expect no phasey sweep or hollow sweeping during each toggle. A small timbre change from Iron itself is expected; the sweep is what to listen for.
2. **In time with other tracks, PDC on (row 29).** Put two copies of a 1 kHz sine at -40 dBFS on separate tracks. Put the plugin on both, with Iron on in one and off in the other. Invert the polarity of the Iron-off copy. Sum both to one bus with PDC on. Expect near silence on the bus (the measured difference in the test is about -68 dB). Then turn PDC off and expect a clear level change, which shows delay compensation is doing the work.
3. **Latency readout (row 27).** Read the plugin latency in the DAW (plugin info or PDC display). Expect 4 samples at 48 kHz.
4. **Bypass does not shift timing (row 30).** Play a kick loop on one track and the same loop on a parallel track with no plugin. With PDC on, toggle the plugin bypass on and off. Expect the kick to stay aligned with the parallel track in both states.

Additional checks from this QA run:

5. **Bypass while playing (row 31).** Play a sustained bass note and a drum loop. Toggle bypass 10 times. Expect no click or dropout.
6. **Mono and stereo (row 32).** Insert one instance on a mono track and one on a stereo track. Repeat steps 1 and 4 on each.
7. **Sample rates (row 33).** Repeat steps 2 and 3 in a 44.1 kHz session and a 96 kHz session. Expect latency 4 and the same null in step 2.
8. **Extremes (row 34).** With Iron on, set Compress / Expand to full compression and then full expansion, and Threshold to its lowest and highest settings. Play a bass and a drum loop. Expect no instability and no clicks.
9. **Session save and reload (row 35).** Set Iron on and bypass off, save, close and reopen. Check Iron is still on. Repeat with Iron off and bypass on.
10. **First CI run (rows 20 and 21).** Push the branch and open a pull request. Confirm the `dsp-tests` job and both `plugin` matrix jobs (Windows and macOS) are green, and that the `processor_tests` ctest entry ran in the plugin jobs.

## Findings

No failing cases. Every automated and code-review case passes. The overall result stays "PASS (manual checks pending)" until the owner runs manual steps 1 to 9 and the first CI run (step 10) is green. Nothing has been pushed in this run, so no CI run exists yet.

1. **Wording of D (decision to confirm, not a failure).** The acceptance text as given to QA reads as ceil of the oversampler latency plus the pole delay, which is ceil(L + g). `src/PluginProcessor.cpp:95-96` describes ceil(L + g) as a deviation from "D = ceil(L)". Those two comments disagree with each other in intent. The two readings give D = 4 here, so no result changes. The operator should confirm the Jira wording and make the code comment match it.
2. **Test 1 checks the formula, not the physics.** `testLatencyReported` recomputes D with the same formula the processor uses (`tests/processor_tests.cpp:114-120`). It confirms wiring and that D is 3 or 4. The physical check is test 6 (alignment), which fails by about 7 dB if the wet path is off by 3.42 samples.
3. **The crossfade test guards against dips only, not timing.** Test 8 uses 1 kHz with both paths aligned. Timing is guarded by test 6. Fade-out direction (Iron on to off) is not automated (test 9, code review only). A test that turns Iron off after a second would close that gap.
4. **Iron-off delay test uses amount 0 only (test 4).** The delay is applied after the compander, so compression should not change it, but the test does not show that with compression on. Manual step 8 covers it by ear.
5. **Block sizes, mono and rates not automated.** All automated tests use stereo, 48 kHz, prepared block 512 with host blocks of 512 or 2048. Host blocks of 1 or 64 samples, mono, and 44.1 and 96 kHz are not automated. Code review passes for each.
6. **Bypass switching during a live signal is not automated.** Tests 10 and 11 start with bypass on. Switching mid-stream is covered only by manual step 5.
7. **Real-time safety is code review only.** No test detects allocation or locking on the audio thread. Checking it needs an allocation hook, which is not in this story.
8. **44.1 kHz and 96 kHz latency is not measured.** The hand calculation assumes the oversampler latency L is unchanged from 48 kHz. The owner's DAW check (step 3 at each rate) is the first measurement.
9. **Not built on MSVC or Apple clang here.** `tests/processor_tests.cpp` was compiled with GCC on Linux only. The first CI run on Windows and macOS is the evidence.
10. **Warnings not fully captured.** The incremental build tail showed no compiler warnings. The full warning log for `src/` was not captured. A clean rebuild with warnings shown would confirm this.
